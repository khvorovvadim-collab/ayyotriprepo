# Концепция: каталог и агент описаний OLAP-кубов и Power BI

Документ фиксирует целевую архитектуру: как версионировать SQL и кубы в GitLab, как собирать метаданные из всех источников и как на этом построить агента, который описывает кубы и дашборды.

Стек, от которого отталкиваемся:

- MS SQL Server (в существующем алерте — `REPORT-S` / БД `ra`, linked server `REPORT-R`)
- Power BI Report Server (on-prem, пути вида `/Product%`)
- OLAP / SSAS (многомерные кубы и/или tabular)
- GitLab как система версий
- Mattermost как канал уведомлений

## 1. Зачем это нужно

Сейчас знание «что считает этот куб / этот отчёт» живёт в головах, в чатах и в разрозненных `.sql` / `.pbix`. Цель агента — не «чат с LLM по папке скриптов», а воспроизводимый каталог витрины:

1. **Инвентарь** — полный список кубов, мер, измерений, отчётов, датасетов, источников.
2. **Линейка (lineage)** — таблица → представление/процедура → мера куба → визуал Power BI.
3. **Описание** — человекочитаемый паспорт объекта: зачем он, какие зерна, какие фильтры, какие ограничения.
4. **Ответы** — агент отвечает на вопросы аналитиков и разработчиков, опираясь на каталог, а не на догадки модели.

Агент без каталога будет галлюцинировать формулы. Каталог без агента останется мёртвым YAML. Нужны оба слоя.

## 2. Что сознательно не делаем в первой версии

- Не генерируем бизнес-смысл «с нуля», если в коде нет ни комментария, ни имени, ни связанного отчёта. Тогда пишем «описание отсутствует» и ставим задачу владельцу.
- Не парсим бинарный `.pbix` как единственный источник истины в runtime. `.pbix` — артефакт публикации; в git должен лежать разбираемый контракт (TMDL / BIM / манифест отчёта).
- Не подключаем агента напрямую к прод-SQL «почитать любые таблицы». Доступ только к метаданным и к уже выгруженному каталогу.
- Не заменяем владельцев метрик. Агент предлагает черновик описания; спорные меры утверждает человек.

## 3. Принцип: два контура

```
┌─────────────────────────────────────────────────────────────┐
│  Контур A. Источники истины в GitLab                         │
│  SQL (SSDT/sqlproj) · SSAS (BIM/XMLA/TMDL) · PBI-контракты   │
└──────────────────────────────┬──────────────────────────────┘
                               │ CI: extract
                               ▼
┌─────────────────────────────────────────────────────────────┐
│  Контур B. Каталог (structured) + паспорта (prose)           │
│  catalog.json · lineage.graph · docs/passports/*.md          │
└──────────────────────────────┬──────────────────────────────┘
                               │ index + RAG + tools
                               ▼
┌─────────────────────────────────────────────────────────────┐
│  Агент (Mattermost / GitLab issue / CLI)                     │
│  «Что считает мера X?» · «Какие отчёты зависят от таблицы Y?»│
└─────────────────────────────────────────────────────────────┘
```

Контур A меняют люди (code review). Контур B собирается пайплайном и частично LLM. Агент **читает B**, а в A ходит только за цитатой исходника.

## 4. Как устроить GitLab (фундамент агента)

Рекомендуемый вариант на старте — **монорепозиторий витрины** (один проект GitLab), а не россыпь репозиториев. Линейку проще строить, когда SQL, куб и контракт отчёта живут рядом. Если политически нужны отдельные репо — тот же layout, плюс каталог-репозиторий, который подтягивает остальные как CI-артефакты.

Предлагаемая структура:

```text
/sql
  /<database>              -- ra, dw, staging, ...
    /Tables
    /Views
    /Procedures
    /Functions
    /Jobs                  -- опционально: T-SQL агентских джобов
/olap
  /<cube-or-model>
    model.bim | *.tmdl     -- tabular
    или *.cube *.dim *.dsv -- multidimensional SSDT
/pbi
  /<workspace-or-folder>   -- зеркало пути PBIRS, напр. Product
    /<report>
      definition.json      -- страницы, визуалы, поля (не .pbix)
      dataset.tmdl         -- если модель в отчёте / shared dataset
      sources.yaml         -- connection strings без секретов
/catalog                   -- генерируется CI, можно коммитить
  catalog.json
  lineage.dot
  /passports
    cubes/
    reports/
/docs
  conventions.md           -- как писать комментарии к мерам и вьюхам
```

Правила, без которых агент деградирует:

1. **Один объект — один файл.** `CREATE VIEW dbo.FactSales AS ...` в `sql/ra/Views/FactSales.sql`, не простыня на 40 объектов.
2. **Имена в git = имена в SQL/SSAS.** Агент матчит объекты по qualified name (`[ra].[dbo].[FactSales]`), а не по «похожему файлу».
3. **Секреты наружу.** Строки подключения в git — только host/db/kind; логины — CI variables / vault.
4. **Комментарии как контракт.** Для мер, расчётных колонок и витрин — короткий header:
   - назначение (1–3 предложения);
   - зерно (grain);
   - фильтры по умолчанию;
   - владелец.
5. **`.pbix` в git — только если нет альтернативы**, и тогда как LFS + рядом обязательный текстовый манифест. Иначе merge и diff бесполезны.

Версионирование кубов:

| Тип модели | Что класть в git | Как снимать с сервера |
|---|---|---|
| SSAS Tabular | `.bim` или TMDL (предпочтительно TMDL) | Tabular Editor / ALM Toolkit / XMLA |
| SSAS Multidimensional | SSDT-проект (`.cube`, `.dim`, `.dsv`, `.ds`) | Visual Studio / XMLA DISCOVER + скрипт |
| Power BI (PBIRS) | манифест отчёта + источники + DAX/TMDL датасета | PBIRS REST / распаковка `.pbix` в CI, не вручную |

Миграции SQL: SSDT (`sqlproj` + dacpac) или Flyway. Для агента формат вторичен, важна **стабильная раскладка файлов** и CI, который на каждый merge в `main` пересобирает каталог.

## 5. Источники метаданных (полный контур)

Агент должен опираться не только на git. Git — канон «как задумано». Серверы — канон «что реально крутится». Расхождения — отдельный отчёт `drift`.

| Слой | Источник | Что извлекаем | Зачем |
|---|---|---|---|
| SQL git | `.sql` / dacpac | объекты, зависимости `FROM`/`JOIN`/`EXEC`, комментарии | описания витрин, lineage вниз |
| SQL live | `sys.views`, `sys.sql_modules`, extended properties | фактический текст, MS_Description | сверка с git |
| SSAS git | BIM/TMDL/XML | таблицы, колонки, меры, DAX/MDX, партиции, источники | паспорт куба |
| SSAS live | XMLA / TOM / AMO | то же + last processed, партиции | drift, свежесть |
| PBIRS catalog | БД ReportServer + REST | путь, имя, тип, датасет, подписки, владельцы | инвентарь дашбордов |
| PBIRS git | манифест отчёта | страницы, визуалы, используемые поля, фильтры | «что показывает отчёт» |
| Алертный контур | уже есть `BI_Report_Refresh_Error` | статус обновления | паспорт «здоровье» |
| Люди | YAML-оверлеи `catalog/overrides/` | бизнес-имя, владелец, домен | то, чего нет в коде |

Приоритет при конфликте:

1. Override человека (`overrides/*.yaml`)
2. Комментарий / annotation в git-исходнике
3. Сгенерированное LLM-описание (помечается `generated: true`, `needs_review: true`)
4. Live-метаданные сервера (для фактов вроде «последний process», не для бизнес-смысла)

## 6. Пайплайн извлечения (детерминированный слой)

Это не LLM. Парсеры и API. Выход — один `catalog.json` (и при необходимости нормализованные таблицы).

Минимальная схема объекта каталога:

```yaml
id: "cube:Sales/measures/Revenue"          # стабильный ID
kind: measure | table | view | report | visual | dataset
name: "Revenue"
qualified_name: "[Sales].[Measures].[Revenue]"
owners: ["team-finance"]
source_files: ["olap/Sales/measures/Revenue.tmdl"]
depends_on: ["sql:ra.dbo.FactSales", "cube:Sales/tables/Date"]
used_by: ["report:Product/SalesDashboard"]
grain: "день × магазин"                    # если известно
expression: "SUM(FactSales[Amount])"       # DAX/MDX/SQL
expression_kind: dax | mdx | sql
description:
  status: human | generated | missing
  text: "..."
tags: ["finance", "revenue"]
freshness:
  last_processed: "2026-08-18T03:00:00Z"
health:
  last_refresh_status: success | error | timeout
```

Шаги CI (GitLab):

1. **Parse SQL** — регулярки + AST (для T-SQL реалистичен гибрид: `sqlglot` ограниченно понимает T-SQL; для зависимостей часто достаточно pragmatic parser + `sys.sql_expression_dependencies` с live).
2. **Parse OLAP** — TOM для tabular; XML для MD.
3. **Parse PBI** — из манифеста: datasetId → поля → визуалы. Live: список отчётов из PBIRS.
4. **Join** — рёбра lineage: SQL object → partition/source куба → column/measure → визуал.
5. **Drift** — git vs live: объект есть на сервере, нет в git (и наоборот).
6. **Generate passports** — LLM только здесь, по шаблону, с цитатами expression и зависимостей.
7. **Publish** — `catalog/` в артефакт и/или commit back в ветку `catalog-bot`; индекс в векторное хранилище агента.

Идемпотентность: один и тот же commit всегда даёт тот же `catalog.json` (кроме блока `freshness/health`, который лучше класть в отдельный `runtime.json`, чтобы не шуметь в diff).

## 7. Генерация описаний (LLM-слой)

Промпт агента-писателя **не** получает весь репозиторий. На один объект:

- qualified name, kind, expression;
- комментарии из исходника;
- список `depends_on` с короткими паспортами соседей (1 уровень);
- список `used_by` (какие отчёты/визуалы);
- предыдущее описание, если было (чтобы не прыгал стиль);
- override, если есть.

Шаблон паспорта куба:

- Назначение и аудитория
- Зерно и ключевые измерения
- Основные меры (формула + словами)
- Источники (БД/таблицы/процедуры загрузки)
- Известные фильтры и исключения
- Связанные отчёты Power BI
- Владелец и статус свежести

Шаблон паспорта отчёта:

- Вопрос, на который отвечает отчёт
- Страницы и что на них
- Датасет / куб / DirectQuery vs Import
- Поля и меры (со ссылкой на паспорт меры)
- Фильтры отчёта по умолчанию
- Расписание обновления и здоровье (из уже существующего алерт-контура)
- Кому эскалировать, если «цифра не бьётся»

Правила качества:

- Каждое утверждение вида «считает X» должно ссылаться на expression или на human-override.
- Если expression есть, а смысл неочевиден — описание + блок `uncertainties`.
- Язык паспортов — русский (как у команды), идентификаторы — как в модели.
- Diff паспорта ревьюится как код, если описание помечено `human`; `generated` можно принимать ботом, но раз в цикл владелец проходит очередь `needs_review`.

## 8. Сам агент (продуктовая форма)

Три режима, один бэкенд.

### 8.1. Каталог (pull)

Markdown-паспорта в `catalog/passports`, плюс страница-индекс. Это «документация, которая не врёт чаще, чем код». Можно публиковать в GitLab Wiki / Pages.

### 8.2. Чат-агент (push/ask)

Канал, который команда уже использует — Mattermost. Сценарии:

- `@bi-bot что считает [Measures].[Revenue] в кубе Sales?`
- `@bi-bot какие отчёты сломаются, если изменить dbo.v_FactSales?`
- `@bi-bot опиши /Product/SalesDashboard`
- `@bi-bot где расхождение git vs сервер?`

Инструменты агента (function calling), не «просто RAG»:

| Tool | Делает |
|---|---|
| `search_catalog` | поиск по имени, тегу, тексту паспорта |
| `get_object` | полный паспорт + expression |
| `get_lineage` | вверх/вниз N уровней |
| `get_source_snippet` | цитата файла из git (только разрешённые пути) |
| `get_refresh_status` | последнее обновление отчёта/куба |
| `list_drift` | объекты без git / без live |

RAG по паспортам — для нечётких вопросов («маржа по рознице»). Точные идентификаторы — только через tools.

Системные ограничения:

- Не выполняет произвольный SQL.
- Не меняет кубы и отчёты.
- Может открывать черновик MR с правкой `overrides/` или комментария в `.sql` / `.tmdl`, если команда это включит позже.

### 8.3. CI-комментарий

На MR в `sql/` или `olap/`: бот пишет «затронутые меры и отчёты» по lineage. Это самый полезный режим для разработчиков и дешёвый по токенам.

## 9. Архитектура сервиса (черновик реализации)

```text
GitLab CI
  extractors (python)
       │
       ├─► catalog.json + runtime.json  ──► object storage / git catalog/
       └─► passports/*.md (LLM)         ──► тот же артефакт
                                              │
                                    indexer (embeddings + keyword)
                                              │
                                    agent-api (Mattermost slash / bot)
                                              │
                                    LLM (внутренний endpoint)
```

Технологический минимум, без лишней платформы:

- Python 3.12, GitLab CI
- Извлечение: `lxml` / JSON BIM, Tabular Editor CLI если доступен в runner, pyodbc только для metadata-query в отдельном job с секретом
- Индекс: с начала — файловый каталог + BM25 (Meilisearch/SQLite FTS); векторы — когда паспортов > порога и появятся «мягкие» вопросы
- Агент: тонкий сервис с tool-calling; Mattermost Incoming + slash, либо outgoing webhook
- Секреты: GitLab CI variables; webhook Mattermost не хранить в git (сейчас он зашит в `PowerBI_ALERT_Mattermost.ps1` — вынести при ближайшем рефакторинге)

Существующий `PowerBI_ALERT_Mattermost.ps1` — не часть агента описаний, а **источник health**. Имеет смысл позже читать `pbix.AlertHistory` / `BI_Report_Refresh_Error` в `runtime.json`, чтобы паспорт отчёта содержал «последняя ошибка обновления».

## 10. Этапы внедрения

Не начинать с чат-бота. Чат без каталога бесполезен.

### Этап 0 — договорённости

- Список кубов и папок PBIRS в скоупе (например, только `/Product%`, как в алерте).
- Владельцы доменов (кто аппрувит паспорта).
- Решение: монорепо vs несколько + catalog-repo.
- Формат кубов: tabular TMDL vs multidimensional SSDT.

### Этап 1 — Git как канон

- Выгрузка SQL-объектов витрины в `/sql` (не всей OLTP-базы).
- Выгрузка определений кубов в `/olap`.
- Для каждого отчёта из скоупа — манифест в `/pbi` (хотя бы имя, путь, dataset, список мер/полей).
- CI: lint раскладки файлов, запрет секретов.

### Этап 2 — каталог без LLM

- `catalog.json` + граф lineage SQL→cube→report.
- Отчёт drift git vs live.
- MR-комментарий «что затронуто».
- Индекс в GitLab Pages: список объектов, зависимости, expression.

На этом шаге команда уже получает ценность: карта системы.

### Этап 3 — паспорта

- Шаблоны + LLM-черновики для кубов и отчётов скоупа.
- Очередь `needs_review` в Mattermost раз в неделю.
- Overrides для спорных метрик.

### Этап 4 — агент

- Mattermost-бот с tools над каталогом.
- Вопросы «что считает» / «кто использует» / «опиши отчёт».
- Подмешивание health из алерт-контура.

### Этап 5 — замкнутый цикл

- Агент предлагает MR в overrides или в комментарии исходников.
- Описание меры живёт рядом с DAX/MDX, а не только в wiki.

## 11. Критерии готовности

Агент можно считать рабочим, когда:

1. 100% кубов и отчётов скоупа есть в `catalog.json`.
2. Для каждой меры с expression паспорт либо human, либо generated+ссылка на формулу.
3. Lineage находит хотя бы один SQL-источник для ≥ N% мер (N согласовать после первой выгрузки; ориентир 70%+).
4. На контрольном наборе из 20 вопросов аналитиков ответы с цитатой исходника, без выдуманных формул.
5. Drift-отчёт пустой по критичным объектам или имеет владельца и срок.

## 12. Риски

| Риск | Как гасим |
|---|---|
| LLM выдумывает смысл меры | Tools + обязательная цитата expression; запрет отвечать без объекта в каталоге |
| `.pbix` не диффится | Текстовый манифест обязателен; pbix только артефакт |
| Неполный T-SQL parse | Live `sql_expression_dependencies` как второй канал |
| Секреты в скриптах и webhook | secret scan в CI; вынести webhook из репозитория |
| Каталог устаревает | Генерация на каждый merge + nightly live-sync |
| Политика «нельзя выгружать куб» | Тогда агент честно помечает объект `source: live-only`, описания хуже |
| Слишком широкий скоуп | Стартовать с `/Product%` и 1–2 кубов |

## 13. Решения, которые нужно принять командой

1. **Tabular или multidimensional** (или оба) — от этого зависит экстрактор.
2. **Монорепо витрины или отдельные git-проекты** SQL / SSAS / PBI.
3. **Где живёт агент** — только GitLab Pages + MR-бот, или сразу Mattermost.
4. **Какая LLM** — внутренний endpoint vs внешний; есть ли запрет выносить SQL во внешний API.
5. **Скоуп v1** — список кубов и папка PBIRS.
6. **Кто владелец метрики** — роль в GitLab CODEOWNERS на `/olap` и `/catalog/overrides`.

Пока эти шесть пунктов не зафиксированы, писать код агента рано; имеет смысл сделать этап 1 (раскладка git + выгрузка).

## 14. Связь с текущим репозиторием

Сейчас в репозитории только скрипт алерта обновления дашбордов (`PowerBI_ALERT_Mattermost.ps1`). Он подтверждает:

- источник отчётов — on-prem PBIRS, не Power BI Service;
- уже есть канал Mattermost;
- уже есть таблица ошибок обновления, пригодная как `runtime.health`.

Этот репозиторий логично либо превратить в монорепо витрины, либо оставить «ops/alerting», а каталог и агент завести отдельным GitLab-проектом, который читает SQL/OLAP-репо как артефакты. Второе чище по правам доступа (алерты ≠ описания мер).
